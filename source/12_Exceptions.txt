## 1. Three kinds of errors

| Kind | When you see it | Example |
| --- | --- | --- |
| **Syntax error** | Before the program even starts. Python cannot understand the code. | Missing `:` after `if x > 3` |
| **Runtime error** | While the program runs. The code is valid, but something goes wrong. | Dividing by zero, `int("abc")` |
| **Logic error** | Never! The program runs, but the answer is wrong. | Forgetting brackets in an average |

A runtime error is also called an **exception**.
Python creates an **exception object** that describes the problem.
If nobody catches it, the program stops and shows the red error box.

This notebook is about runtime errors, because those are the ones you can **catch** and handle.

@@ predict A logic error
This code is meant to print the average of 80 and 90.
@@ run

mark2 = 90
average = mark1 + mark2 / 2
print(average)
@@ output
125.0
@@ explain
There is no red error box, so Python is happy.
But the answer is wrong: the average should be `85.0`.
`/` is done before `+`, so Python works out `80 + 45.0`.
This is a **logic error**. Python cannot find it for you, you must test your code.

## 2. The built-in exceptions you must know

| Exception | Usual cause | Example |
| --- | --- | --- |
| `ValueError` | Right type, wrong value | `int("abc")` |
| `IndexError` | List position does not exist | `[1, 2, 3][5]` |
| `KeyError` | Dictionary key does not exist | `{"a": 1}["b"]` |
| `ZeroDivisionError` | Dividing by zero | `10 / 0` |
| `TypeError` | Wrong type for the operation, or wrong number of arguments | `"Age: " + 19` |
| `NameError` | A name that does not exist | `print(prise)` |
| `AttributeError` | The object has no such attribute or method | `"hi".push()` |

## 3. Catching an exception with `try` and `except`

Put the risky code inside `try:`.
If an exception happens, Python **jumps** straight to the `except:` block.
The program then carries on normally instead of crashing.

```python
try:
    # code that might fail
except ValueError:
    # what to do if it fails
```

@@ code
text = "abc"
try:
    qty = int(text)
    print("You ordered", qty)
except ValueError:
    print("Please type a whole number")
print("The program is still running")

@@ md
Notice that `print("You ordered", qty)` did **not** run.
As soon as `int(text)` failed, Python jumped to `except`.

**Getting the message.**
Write `except ValueError as e:`.
Now `e` is the exception object, and `print(e)` shows its message.

@@ code
try:
    qty = int("abc")
except ValueError as e:
    print("Error:", e)

@@ predict Which lines run?
@@ run

    x = 10 / 0
    print("B")
except ZeroDivisionError as e:
    print("C", e)
print("D")
@@ output
A
C division by zero
D
@@ explain
`A` is printed.
The division fails, so Python jumps to `except` and skips `B`.
`C` is printed with the message of the exception, `division by zero`.
After the `try` / `except`, the program carries on, so `D` is printed.

## 4. The full shape: `try`, `except`, `else`, `finally`

```python
try:
    # risky code
except SomeError as e:
    # runs ONLY if that error happened
else:
    # runs ONLY if NO error happened
finally:
    # ALWAYS runs, error or not
```

`else` and `finally` are optional.

| What happened in `try` | Blocks that run |
| --- | --- |
| No error | `try` (all of it), then `else`, then `finally` |
| An error that is caught | `try` (up to the error), then `except`, then `finally` |

💡 Remember: **`finally` always runs.**
It runs even when there is a `return` inside `try` or `except`.

The next four predictions come from the seminar slides.
The exam has asked questions exactly like them.

## 5. Several `except` blocks, and why the order matters

One `try` can have several `except` blocks, one for each kind of error.
Python checks them **from top to bottom** and uses the **first one that matches**.

`except Exception` matches **every** normal error.
So if it comes first, the more specific blocks below it can never run.

**Rule: put the specific exceptions first, and `Exception` last.**

@@ code
def readPrice(text):
    try:
        price = float(text)
        return 100 / price
    except ValueError:
        return "not a number"
    except ZeroDivisionError:
        return "cannot be zero"
    except Exception:
        return "something else went wrong"

print(readPrice("4"))
print(readPrice("abc"))
print(readPrice("0"))

@@ predict General first
@@ run

    x = float("hello")
except Exception as e:
    print("Caught by Exception")
except ValueError as e:
    print("Caught by ValueError")
@@ output
Caught by Exception
@@ explain
A `ValueError` **is a kind of** `Exception`.
Python checks the blocks from the top, and `except Exception` already matches.
So the `except ValueError` block can never be reached. This is a mistake in the code.

### The exception family tree

Exceptions are classes, and they use **inheritance** (notebook 10).
Here is part of the family tree:

```text
Exception
 +-- ArithmeticError
 |    +-- ZeroDivisionError
 +-- LookupError
 |    +-- IndexError
 |    +-- KeyError
 +-- ValueError
 +-- TypeError
 +-- AttributeError
 +-- NameError
```

`except X` catches `X` **and every class below it** in the tree.
So `except LookupError` catches both `IndexError` and `KeyError`.

    except Exception:

not found

@@ explain
`[10, 20][5]` raises an `IndexError`, which is a kind of `LookupError`.
`{"a": 1}["b"]` raises a `KeyError`, which is also a kind of `LookupError`.
`[10, 20]["x"]` raises a `TypeError` (a list position must be a number). That is not a `LookupError`, so the second block catches it.

## 6. Your own exceptions and `raise`

Python's errors are about Python problems, like dividing by zero.
Your program also has **business rules**, for example:

- A cash card balance cannot go below zero.
- A student cannot join more than 3 CCAs.

When a rule is broken, you **raise your own exception**.

**Step 1: make the exception class.**
It inherits from `Exception`. It needs nothing inside, so the body is just `pass`.

```python
class CashCardException(Exception):
    pass
```

**Step 2: raise it with a clear message.**

```python
raise CashCardException("Insufficient balance")
```

`raise` stops the current code **immediately**, just like a built-in error.
The message you give becomes the text of `e` when someone catches it.

@@ code
class CashCardException(Exception):
    pass

def checkAmount(amount):
    if amount <= 0:
        raise CashCardException("Amount must be positive")
    print("Amount is OK")

try:
    checkAmount(10)
    checkAmount(-5)
    checkAmount(20)
except CashCardException as e:
    print("Error:", e)

@@ md
Notice that `checkAmount(20)` never ran.
After the exception, Python jumped straight to `except`.

⚠️ **`raise` is not `print`.**
If the question says "raise an exception", printing a message is wrong and loses the marks.
The method raises, and the **caller** decides whether to print.

## 7. Raising inside a class

In the exam, you raise exceptions inside **methods** of a class.
There are three common places:

1. **In `__init__`**, so a bad object is never created.
2. **In a setter**, so a property cannot be set to a bad value.
3. **In a normal method**, such as `deduct` or `add`.

@@ code
class CashCardException(Exception):
    pass

class CashCard:
    def __init__(self, cardId, balance):
        if balance < 0:
            raise CashCardException("Balance cannot be negative")
        self.__cardId = cardId
        self.__balance = balance

    @property
    def balance(self):
        return self.__balance

    def deduct(self, amount):
        if amount > self.__balance:
            raise CashCardException(f"Insufficient balance: ${self.__balance:.2f}")
        self.__balance -= amount

    def __str__(self):
        return f"Id: {self.__cardId} Balance: ${self.__balance:.2f}"

try:
    card = CashCard("C1", 10)
    card.deduct(4)
    print(card)
    card.deduct(50)
    print(card)
except CashCardException as e:
    print("Error:", e)

@@ md
The second `print(card)` never runs, because `deduct(50)` raised the exception first.

💡 Look at the order inside `deduct`: **check first, then change**.
If you subtract first and check afterwards, the balance is already wrong when the error is raised.

class BoxException(Exception):
    pass

class Box:
    _MAX_ITEMS = 10

    def __init__(self, numberOfItems):
        if numberOfItems > Box._MAX_ITEMS:
            raise BoxException("Box cannot hold more than 10 items")
        self.__numberOfItems = numberOfItems

    @property
    def numberOfItems(self):
        return self.__numberOfItems

    def add(self, items):
        if self.__numberOfItems + items > Box._MAX_ITEMS:
            raise BoxException("Box is full")
        self.__numberOfItems += items

    def remove(self, items):
        if self.__numberOfItems - items < 0:
            raise BoxException("Not enough items")
        self.__numberOfItems -= items

## 8. Where to catch: the exception travels up

When a method raises an exception and does **not** catch it, the exception leaves the method.
It goes **up** to the code that called the method.
If that code does not catch it either, it goes up again, until someone catches it or the program crashes.

```text
main()          <- try / except here catches it
  calls addContact()       <- no try here, the exception passes through
    calls Contact()        <- raise happens here
```

🎯 Exam questions often say **"Do not handle the exception in this method."**
That means: **no `try` in that method**.
Just `raise` (or let it pass through), and the caller will handle it.
Writing a `try` there loses marks.

@@ predict The exception passes through
@@ run

    print("added", name)

    try:
        addItem("Tea", 2)
        addItem("Cake", -1)
        addItem("Juice", 3)
    except PriceException as e:
        print("Error:", e)

## 9. The checks the exam always asks for

These checks come up in almost every paper.
Learn the exact `if` line for each one.

| Rule in the question | The check |
| --- | --- |
| "This addition results in more than the maximum" | `if len(self.__items) + 1 > Shop._MAX:` |
| "Fewer than the minimum after removal" | `if len(self.__items) - 1 < Shop._MIN:` |
| "Total over a cap" | `if self.total() + item.price > Shop._CAP:` |
| "Duplicate name" | search first: `if self.search(name) is not None:` |

The sample output in the paper depends on that order.

⚠️ **Copy the message text exactly** when the paper gives it, including capital letters and full stops.

## 10. The main program: keep going after an error

In the exam, the last part often says: "Write a `main()` that creates objects, calls the methods, and handles the exceptions."

**Where you put `try` decides what happens after an error.**

- `try` **around** a loop: the first error stops the whole loop.
- `try` **inside** a loop: each item gets its own chance, and the loop keeps going.

## 11. A family of your own exceptions

A bigger program can have one **base** exception, with more specific ones below it.
This uses inheritance, exactly like Python's own family tree.

```python
class VehicleException(Exception):
    pass

class SpeedingException(VehicleException):
    pass
```

- `except SpeedingException` catches only speeding problems.
- `except VehicleException` catches **both**, because a `SpeedingException` is a `VehicleException`.

The same rule as before: the specific one goes **first**.

@@ solution
class Student:
    _MAX_CCA = 3

    def __init__(self, studentId, name):
        self.__studentId = studentId
        self.__name = name
        self.__ccas = []

    @property
    def studentId(self):
        return self.__studentId

    def searchCCA(self, ccaName):
        for cca in self.__ccas:
            if cca.name.lower() == ccaName.lower():
                return cca
        return None

    def enrol(self, cca):
        if self.searchCCA(cca.name) is not None:
            raise EnrolmentException(f"Already enrolled in {cca.name}")
        if len(self.__ccas) + 1 > Student._MAX_CCA:
            raise EnrolmentException(f"Cannot enrol more than {Student._MAX_CCA} CCAs")
        self.__ccas.append(cca)

    def withdraw(self, ccaName):
        cca = self.searchCCA(ccaName)
        if cca is None:
            raise EnrolmentException(f"Not enrolled in {ccaName}")
        self.__ccas.remove(cca)
        return cca

    def totalFees(self):
        total = 0
        for cca in self.__ccas:
            total += cca.fees
        return total

    def __str__(self):
        return f"{self.__studentId} {self.__name}: {len(self.__ccas)} CCA(s), total fees ${self.totalFees():.2f}"

## 📝 Key points

- **Syntax** errors stop the program before it starts. **Runtime** errors (exceptions) happen while it runs. **Logic** errors give wrong answers with no message.
- `try:` holds the risky code. `except X as e:` runs only if `X` happened, and `print(e)` shows the message.
- `else` runs only if there was **no** error. `finally` **always** runs, even after a `return`.
- Put specific `except` blocks first and `except Exception` last.
- Your own exception: `class XException(Exception): pass`.
- `raise XException("message")` stops the method at once. It does **not** print anything by itself.
- An exception you do not catch travels **up** to the caller. "Do not handle it here" means no `try` in that method.
- Check first, then change. Follow the order of checks in the question and copy the message text exactly.
- `try` **inside** a loop lets the loop carry on after an error.

## ⚠️ Common mistakes

| Mistake | What goes wrong |
| --- | --- |
| `print("Too many")` instead of `raise ...` | No exception, and the bad change still happens |
| `if len(self.__items) > MAX:` before adding | Lets the list grow one too big. Use `len(...) + 1 > MAX` |
| `except Exception` first | The specific blocks below can never run |
| `class XException:` (no `(Exception)`) | `TypeError` when you raise it |
| A `try` inside the method when told not to handle it | Loses marks, and the caller never hears about the error |
| Typing `3` instead of `Student._MAX_CCA` | Marker looks for the class variable |
| Changing the list, then checking | The data is already wrong when the error is raised |
